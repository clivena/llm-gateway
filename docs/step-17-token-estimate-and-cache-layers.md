## 缺陷 1 · 配额估算的两个缺陷

### 现象

同一个中文问题问两遍，账本里的 `prompt_tokens` 与真实值差得很远；
且**消息条数越多，偏差越大**。

### 根因

旧实现是 `Math.max(1, question.length() / 4)`，两处错：

1. **公式是英文的**。`length/4` 来自"1 token ≈ 4 个英文字符"的经验值。
   中文一个字往往是 1~2 个 token，`length/4` 直接把中文**低估数倍**。
2. **只算了最后一条 user 消息**。system prompt、历史轮次全部视而不见。
   多轮对话里，真正的 prompt 开销大部分在历史里。

两处叠加，导致配额预扣与实际开销脱钩。预扣过低 → 配额上限形同虚设，
用户可以在"还有额度"的假象下把上游账单跑爆。

### 修法

`TokenEstimator` 按内容分类加权，而不是按字符数一刀切：

```
weighted = baseOverhead                      // 一次性
         + Σ ( perMessageOverhead
             + weightedChars(role) + weightedChars(content) )
```

`weightedChars` 用 `codePoint`（不是 `char`）遍历，汉字/全角/假名/谚文
记一个系数，其余记另一个。用 `codePoint` 是因为 emoji 等补充平面字符
在 Java 里占两个 `char`，按 `char` 遍历会把它们数成两个字符。

系数全部走配置（`gateway.token-estimate`），因为 token 数由**上游分词器
与模板**共同决定，换供应商必须重新校准——写死在代码里等于把一次实测
结论当成了普适真理。

## 发现 · 真正的主导项是一次性模板开销

这是本批最重要的一条，它**推翻了上一轮的错误归因**。

### 证据

上一轮把偏差记作"中文被低估 6.43 倍"，暗示问题在换算系数。校准探针里
有一条 `"Explain caching"`——**15 个纯 ASCII 字符，没有任何中文**。
按任何英文字符换算公式它都该是 4 个 token 左右。上游回传的是 **32**。

用六组探针列方程，解出：

```
prompt_tokens ≈ 26.5 + 1.16 × 消息数 + 0.512 × 汉字数 + 0.188 × 其他字符数
```

`26.5` 与内容完全无关，每个请求只付一次——那是上游把请求套进自家
对话模板产生的固定成本。对短请求它**绝对主导**（5 字提问里占 80%）。
反过来看，"28 个汉字"其实只值 15 个 token，加 29 的固定开销才成为 45。
所以偏差的主因是**漏了一项**，不是**系数错了**。

> 归因错会导致修错地方：如果只去调汉字系数，短请求会永远差一大截
> 而长请求反而被调过头。README 的"已知边界"里已标注此前归因不准确。

### 校准结果

`scripts/calibrate-token-estimator.py` 六组探针（中文短/长、英文短/长、混合、
多消息），脚本**从 `/admin/pricing` 回读生效系数**再复现 Java 侧公式——
而不是在脚本里硬编码一份副本。硬编码副本的脚本只能验证"脚本自己算得对"。

| 探针 | 估算/真实（旧公式） | 估算/真实（新模型） |
|---|---|---|
| 中文短 | 0.15 | **1.00** |
| 中文长 | 0.23 | **1.00** |
| 英文短 | 0.09 | **1.03** |
| 英文长 | 0.64 | **1.02** |
| 混合 | 0.23 | **1.00** |
| 多消息 | 0.04 | **1.01** |

## 缺陷 2 · 缓存在真机上一次都没命中过

### 现象

配置里 `cache.enabled: true`，服务正常启动，请求正常返回，
**但 Redis 里一个缓存键都没有**。

### 根因

缓存的唯一实现依赖 embedding（`/embeddings` 端点取向量），
而当前供应商 DeepSeek **没有这个端点**（实测 404）。

于是每个请求都要走"试遍所有 adapter 取向量 → 全部失败 → 返回空 Mono → MISS"
的路径。**开着但永远不命中**，而所有指标都正常。

### 修法

拆成两层，`CacheLayer` 接口 + `@Order` 排序：

| 层 | 机制 | 依赖 | 定位 |
|---|---|---|---|
| L1 精确 | 规范化 → SHA-256 → Redis 单键 | 无 | **默认层，必然可用** |
| L2 语义 | 向量检索 + 相似度阈值 | `/embeddings` | 可选增强 |

L1 让"同一个问题问两遍"这个最常见场景真正免费——它不需要任何外部能力。
L2 保留但不默认依赖，配置里可独立开关。

### 两个刻意的设计取舍

**① 规范化只做保守变换。** 缓存最坏的失败模式是**错答案**（漏命中只是少省钱，
错命中的后果是把 A 问题的答案给了 B）。所以 L1 只做 `trim` + 空白折叠 +
ASCII 大小写归一，**刻意不剥标点**。"这是对的" 与 "这是对的？" 是两个问题，
模糊匹配交给有阈值兜着的 L2。

**② 层间串联必须用 `concatMap` 而不是 `flatMap`。** `concatMap` 命中即短路；
用 `flatMap` 的话 L1 已命中时仍会并发去调 L2 —— 那是一次**要花钱的** embedding
调用。测试里专门断言了这一点（`L1 命中后 L2 的 lookups 必须为 0`）。

### 顺带修掉的静默早退

`writeCache` 原本在"缓存关闭 / 答案为空"时静默 `return`。这次把它改成
`log.warn`，带上是哪个条件不满足：

```
cache write skipped [ns=diag-cache-2:deepseek-flash]: cacheEnabled=true answerBlank=true
```

这条日志**刻意保留**——它把"缓存开着但从不写入"从不可观测变成一眼可见。
调试时正是靠它定位到下游问题的（见"新发现"）。

## 缺陷 3 · WebFlux 下 MDC 里没有 traceId

### 根因

MDC 基于 `ThreadLocal`，前提是"一个请求一个线程"。WebFlux 下线程是复用的，
MDC 放进去了也不会在正确的位置被读到。

### 修法

用 Reactor 官方的 `MdcContextLifter` 模式：`Hooks.onEachOperator` 注册一个
`CoreSubscriber` 装饰器，在 `onSubscribe/onNext/onError/onComplete` 四个入口
都从 **Reactor Context** 同步一次 MDC。

两个细节：

- `Hooks.onEachOperator` **同 key 重复注册会抛异常**，所以先
  `resetOnEachOperator` 再注册，让装配幂等（测试会重建上下文）。
- 没有 traceId 时要 `MDC.remove` 而不是保留上一轮的值——否则异步边界上
  会把**上一个请求**的 traceId 带到这个请求的日志里，比没有更糟。

## 缺陷 4 · 延迟与拒绝都没有指标

`GatewayMetrics` 补两项：

- `llmgw.request.latency`（Timer，按 `model` / `stream` 打标，
  `publishPercentiles(0.5, 0.95, 0.99)`）——三条路径都记：缓存命中、
  非流式分发、流式分发。
- `llmgw.quota.rejected`（Counter）——配额拒绝此前只有日志没有指标。

**延迟指标必须独立于账本。** 账本链路挂掉的时候，恰恰是最需要看延迟的时刻；
如果延迟数据也走账本，那故障期就同时失去两个观测面。

## 实测验证

### 估算精度

`python scripts/calibrate-token-estimator.py` —— **六组全部 PASS**，
比值 1.00 / 1.00 / 1.03 / 1.02 / 1.00 / 1.01。

### 缓存命中

`python scripts/check-cache-layers.py` —— **8/8 PASS**。

| 用例 | 期望 | 第一次 | 第二次 |
|---|---|---|---|
| 完全相同 | 命中 | 15752ms | **39ms** |
| 首尾空格 | 命中 | 10327ms | **14ms** |
| 连续空白 | 命中 | 19430ms | **64ms** |
| 英文大小写 | 命中 | 4738ms | **48ms** |
| 标点不同 | 不命中 | 15829ms | 22108ms（走上游） |
| 内容不同 | 不命中 | 13958ms | 13583ms（走上游） |
| 换模型 | 不命中 | — | 22552ms（走上游） |

命中时 **快 250~400 倍**、usage 全 `0/0`、账本留下 `cache_hit=true` 的行。
命中判定用**三重交叉验证**（响应头 + 明显更快 + 未计费）——只看响应头的话，
一个"永远返回 true 的 bug"也能骗过测试。

脚本设计的两个细节：每组用**独立租户**（namespace = 租户:模型），
避免组间互相污染；用例里**刻意包含三组"不该命中"**，因为精确缓存的失败模式
是错答案而不是漏命中。

## 新发现 · 上游是推理型模型（本批未修，已列入 B 批）

调试缓存时挖出来的，比缓存问题本身更大。

### 现象

把探针的 `max_tokens` 从 8 提到 64 后，仍然 `completion_tokens=64` 且
`content` 为空字符串。缓存因此没有东西可写，表现与"缓存失效"一模一样。

### 根因

上游响应里带 `reasoning_content` 字段——**这两个模型都是推理型**，
而 `max_tokens` 是**"推理 + 正文"的总预算**，不是只算正文。

`scripts/probe-upstream-shape.py` 扫描结果：

| 模型 | max_tokens=512 | 1024 | 2048 | 4096 |
|---|---|---|---|---|
| `deepseek-flash` | 空（仅推理） | 空（仅推理） | 217 字 | 1220 字 |
| `deepseek-v4-pro` | 空（仅推理） | 1514 字 | 2483 字 | 2639 字 |

推理 token 数还高度不确定（flash 在 512 / 1024 / 1935 / 1740 之间跳），
所以"看起来够大"的 1024 也可能一个正文字都不出。

### 由此暴露的两个真实缺口

**① `finish_reason` 被丢弃。** `OpenAiAdapter.toChatResponse` 只取
`message.content`，`finish_reason` 和 `reasoning_content` 都没带出来。
于是**"被截断导致的空正文"与"模型真的什么都没说"在客户端完全一样**。
而 `finish_reason: length` + 空正文恰恰是推理模型最常见的失败形态。

**② 配额只扣 prompt，completion 从不入账。** `QuotaService.tryConsume`
是唯一写入配额键的地方，`currentUsage` 只读，**全项目没有任何结算/补扣步骤**。
而实测 completion 是 prompt 的 **20~100 倍**：

| 请求 | prompt | completion |
|---|---|---|
| 完全相同 | 33 | 2172 |
| 连续空白 | 37 | 3200 |
| 标点不同 | 34 | 3516 |
| 模型隔离 | 87 | 1481 |

也就是说配额计量只覆盖了实际 token 量的百分之几。这直接关系到
`gateway.quota.default-limit-tokens` 这个数字**到底约束了什么**。

②与 B 批的 F1/F2 是同一个问题域——"什么算失败"。空正文被当成成功，
熔断和故障转移就永远不会在真实最常见的失败上触发。

---

## 从这批里抽象出的 2 条原则

1. **"配置正确"与"功能生效"是两件事。** 缓存那次失效，配置是对的、日志是干净的、
   接口是 200 的，唯一的异常现象是"什么都没发生"。所以每个"生效型"部件都该
   有一个**能证伪**的断言：不是"服务起来了"，而是"第二次请求真的 40ms 返回且未计费"。

2. **估算类逻辑必须能被外部实测反推。** 系数放在配置里、脚本从 `/admin/pricing`
   回读、再把反推值与代码默认值对比——三方对不上就说明有一处已经漂移。
   如果脚本硬编码一份系数副本，它验证的只是"脚本自己和自己一致"。
