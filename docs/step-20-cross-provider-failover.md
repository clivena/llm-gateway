# step-20 · 跨 provider 故障转移（F2）

> 承接 [step-19 重试与熔断](./step-19-retry-and-circuit-breaker.md)（F1）。
> F1 解决了"**这家**不行的时候要不要再试一次"，F2 解决"**这家**不行的时候还有谁"。

## 1. 目标与范围

B 批的 F2，用户确认的三条边界：

| 决策点 | 选择 | 理由 |
|---|---|---|
| 与级联升级的关系 | **只做同模型换 provider** | 转移 = "同样的请求换个地方发"，与"降级/升级换模型"是两件事。混在一条链上会让配额与缓存的语义变模糊，也会动到 F0 已稳定的升级路径 |
| 空正文是否触发转移 | **触发** | "上游 200 但模型什么都没产出"是模型侧问题，换个部署完全可能正常 |
| 调用次数上限 | **双重上限**：`max-providers=2` + `max-total-attempts=4` | 重试次数与候选家数是**相乘**关系（3×3=9）。只限一个方向，另一个方向可以无限放大 |

不在范围内：跨模型转移、按健康度动态排序、权重/轮询、候选预检。

## 2. 前置发现：候选链根本存不下来

F2 的第一个改动不是写转移逻辑，而是改一个数据结构。`ProviderRegistry` 原本是：

```java
private final Map<String, ProviderAdapter> byModel;
...
ProviderAdapter owner = index.putIfAbsent(model, adapter);
if (owner != null) {
    log.warn("模型 {} 在多家 provider 下重复声明：采用先声明的 {}，忽略 {}", ...);
}
```

**同模型的第二家 provider 会被 warn 然后丢掉。** 这个设计在"只想挑一家"的语义下没错，
但它让"同模型多部署"这个配置**根本表达不出来**——写完配置、启动日志也打了、请求也不报错，
只是第二家永远不会被用到。

它还有一个更阴险的地方：如果先写完 F2 的转移逻辑再来改这里，测试会全绿而真机永远不转移。
所以顺序必须是**先改数据结构、再写算法**。

改动：

- `byModel` → `Map<String, List<ProviderAdapter>>`，值是**候选链**（顺序 = 声明顺序）
- 新增 `candidatesFor(model)`；`forModel(model)` 保留为 `candidatesFor(model).get(0)`
  （缓存层取向量模型、启动期校验这类"只想挑一家"的地方语义不变，既有 124 条测试不用动）
- 重复声明从 `warn 忽略` 改成 `info 登记为故障转移候选`
- 唯一真正该报警的重复是 **base-url 相同**：同一份出口挂了两次名，转移过去只会得到同一个失败
- 同一家 provider 在自己的 `models` 里把同一个模型名写两遍 → 去重（否则候选链里会出现两个一样的候选）

## 3. 转移谓词：包含重试谓词，但不等于它

```java
failoverable = retryable ∪ {熔断打开}
```

两个方向的直觉都要过一遍才成立：

| 错误 | 可重试 | 可转移 | 为什么 |
|---|---|---|---|
| 5xx / 429 / 连不上 / 超时 / 空正文 | ✅ | ✅ | 同一家再试一次可能好，那换一家就**更**可能好 |
| **熔断打开** | ❌ | ✅ | 重试仍进不去熔断器（窗口还开着），只会空转烧预算；但换一家是完全不同的链路，那家好好的就该让它上 |
| 4xx（400/401/404）/ 参数非法 | ❌ | ❌ | 网关发出去的请求没变，换一家会拿到**一模一样**的错误，转移只是把同一份失败多买一次 |

中间那一行是 F2 最容易写错的地方：顺手写成 `failoverable = retryable`（"熔断打开也是一种错嘛"）
会让**熔断加上了、转移永远不生效**——一次链路故障依然等于整站失败。

它也是"熔断与转移必须成对存在"的正式表述：
**熔断负责"不再问这家"，转移负责"那接下来问谁"。**
只有熔断没有转移 = 一次链路故障变成整站不可用；只有转移没有熔断 = 对着一条已确认坏掉的链路反复冲。

## 4. 四层嵌套，每层回答一个问题

```
转移（最外）  ← F2：还有谁可以问
  重试        ← F1：同一家要不要再试一次
    熔断      ← F1：这条链路现在还值得试吗
      超时    ← F1：多久算它不回话
```

三个"反过来就错"的地方（前两个 F1 已经写过，第三个是 F2 新增）：

1. **熔断在内、重试在外**：否则一次逻辑请求无论内部重试几次都只记 1 笔，失败率被系统性稀释。
2. **超时在最内**：否则 3 次重试的总耗时可达 `3 × timeout`。
3. **转移必须在重试之外**：真机断言"桩A收到 3 次而不是 1 次"就是这一条的证明——
   先在同一家把重试预算用完，才换地方。反过来会表现为桩A只收到 1 次，
   而那意味着"一抖动就换家"，备选会被无谓地消耗掉。

## 5. 请求级预算：扣减法

上限不能落在 provider 级，否则乘法照旧成立。做法是**按候选顺序递减分配**：

```
预算 = 4（max-total-attempts）
链首：granted = min(3, 4) = 3，预算 → 1
备选：granted = min(3, 1) = 1，预算 → 0
最终：整条链最多 4 次上游调用
```

**为什么要"扣减"而不是"事后统计"**：重试算子内部的计数对外不可见，想知道"这次实际用了几次"
就得把 resilience4j 的内部状态泄漏到编排层。扣减法宁可少给备选一次机会，
换一个**可以静态算出的上限**——故障期的账单能算出来，比多给备选一次重试重要得多。

两个上限必须一起配，因为只配一个会各留下一个可以无限放大的方向：
候选家数越多（宽度）或 `max-attempts` 越大（深度）。默认 4 与默认 `max-attempts=3`
的关系是刻意算过的：链首拿 3 次，剩 1 次留给备选——备选只探一次就够回答
"是不是整条链路都坏了"。

### OPEN 的候选要**跳过**，而不是"试一次被拒再换家"

后者看起来更省事（复用一个错误路径），但代价是隐蔽的：被熔断器拒绝的调用**根本不出网**，
却仍然按分配额扣掉预算，于是备选只剩 1 次机会——**主力长时间不可用的时候，
每个请求都会被静默削掉重试能力**。真机 C2 断言"桩A 3→3、桩B 1→2"就是钉这一条。

跳过的同时要记账（`circuit.rejected` + warn 日志），否则"有多少请求被踢出首选链路"就查不到了。

HALF_OPEN **不能**一并跳过：半开的定义就是"放几个探针看看恢复了没"，
探针被跳过，熔断器永远等不到那几次成功、永远回不到 CLOSED——
一个能自愈的状态变成永久黑洞，而表面症状只是"流量都走了备选"。

## 6. F0 的透传与 F2 的转移，顺序不能反

这是本批次抓出来的**真实设计冲突**，也是唯一一处必须在代码里显式调整的地方。

F1 里"空正文"的处理是这样的：

```java
return resilience.protect(adapter.name(), attempt)          // 内部重试
        .onErrorResume(UpstreamEmptyResponseException.class,
                       e -> Mono.just(e.response()));        // 重试耗尽 → 还原原始响应
```

还原 = "放弃这次请求，如实把上游说的原因交给客户端"（F0 的 `200 + finish_reason=length` 透传）。

到了 F2 这里出问题了：**还原成一个成功值之后，外层拿到的就是成功，再没有机会去问下一家。**
于是"换个部署就能拿到正常答案"的请求，被当成"上游明确说了它答不出"直接交付给客户端。
第一次跑 F2 单测时 `emptyAnswerTriggersFailover` 就是这么红的。

修法是把还原从"单次调用内部"挪到"整条候选链的末端"：

```java
// callUpstream：不再还原，让异常穿出去，转移才有机会
return resilience.protect(adapter.name(), attempt, attempts);

// attemptChain：每一个"放弃继续转移"的地方都走 terminal
private static Mono<ChatResponse> terminal(Throwable e) {
    if (e instanceof UpstreamEmptyResponseException empty) {
        return Mono.just(empty.response());     // 重试与转移都试过了，才如实交付
    }
    return Mono.error(e);
}
```

正确的顺序是：**先穷尽转移，再还原响应。** 反过来就把 F0 建立的东西吃掉了。

## 7. 流式闸门必须跨 provider 共享（F2 最可能的回归点）

F1 里 `upstreamProduced` 这个 `AtomicBoolean` 的生命周期是"一次 `protectStream` 调用"——
那时候候选只有一家，没区别。到 F2，如果每次换 provider 都新建一个标记：

```
a 吐了 3 个正文分片 → 报错 → 新标记是 false → "闸门是开的" → 换 b 重放一遍
```

客户端收到**两段拼接的答案**，而服务端日志里只有一条漂亮的 `failing over a→b、最终成功`。
F1 已经把这唯一路径上的重复推送防住了，F2 如果各建各的标记，
就会从**故障转移这条新路径**上把同一个 bug 放回来。

所以标记必须**跨整个请求**共用（包括级联升级那一段）。
真机 B5 是专门为它设计的：让桩A吐一帧后按 `Content-Length` 截断连接，
制造出"首帧已送达 + 报错"这个真机上唯一的场景，断言**桩B 一次都没被调用**。

> 用 `upstreamProduced`（任何帧都算）而不是 `emitted`（只有正文帧算）当闸门，
> 是因为转移比重试更"重"（换的是另一家的模型）：只要有过任何输出，
> 重放都可能让客户端看到两段不同来源的内容，宁可不救。

## 8. 失败路径的配额（不变量 E）

一次逻辑请求**只预扣一次**，但故障期它可能真的打给了 2 家上游（都计费）。
结算口径沿用 F1：

- `spentTokens > 0`（拿到过真实用量）→ 用真值
- `neverReachedUpstream`（熔断打开 / 连不上）→ 全额退还
- 其余 → 保守保留预扣

新增的已知取舍：**故障期用户实际消耗可能超过配额上限**（预扣是按单次算的）。
方向和 F1 一致——少扣可追，多扣不可逆。见第 10 节。

## 9. 验证

`scripts/check-failover.py` —— **13/13 PASS**。分四段跑（四次启动服务），
因为四类问题需要四种不同的环境才能回答：

### A 段 · 真实上游（DeepSeek）：候选顺序是不是真的等于优先级

| 断言 | 结果 |
|---|---|
| A1 链尾坏候选**零代价**（候选链 = [真实, 不可达]） | HTTP=200 正文 45 字 **转移 0 次** |
| A1' 面板列出两家候选 | `providers=['deepseek', 'provider-dead']` |
| A2 链首不可达 → **透明转移**（候选链 = [不可达, 真实]） | HTTP=200 正文 57 字 **转移 1 次 retry+2 耗时 4782ms** |

这一对是本节最有信息量的数据：**同样两家候选，只是顺序不同，代价从"零"变成"约 5 秒"**
（链首要先把 3 次重试预算烧完才轮到备选）。好处是后续熔断会接管这段开销，
代价是故障刚开始的那几个请求会明显变慢。这就是"顺序即优先级"的直接后果。

A1 还顺手守住了"候选链不会被遍历/探测"：如果实现是"先把候选都探一遍再挑"，
链尾多一家坏的也会让**每个**请求都变慢。

### B 段 · 两个本地桩：转移了几次、总预算是多少

| 断言 | 结果 |
|---|---|
| B0 覆盖生效 + **正常路径不转移** | 桩A=1 桩B=0 |
| B1 **转移真的换了另一家** | 桩A=**3** 桩B=**1** 正文='桩B的答案'，failover +1、retry(A) +2 |
| B2 跨 provider **总预算**生效 | HTTP=502 总调用=**4/4**（无上限则为 6） |
| B3 确定性 4xx **不转移** | 桩A=1 桩B=**0** |
| B4 流式首片前转移，**正文不重复** | 正文='桩B的答案流式后半段' 桩A=3 桩B=1 |
| B5 **首帧后不转移**（闸门） | 客户端收到'首帧已送达' 桩B=**0** |
| B6 failover 指标带**方向**标签 | a→b=3.0 b→a=0.0 |

B1 的"桩A=3"和 B4 的"桩A stream=3"是"重试在内、转移在外"的证据；
B5 的"桩B=0"是"标记跨 provider 共享"的证据——这两条都是**只靠看代码看不出来**的。

### C 段 · 两个本地桩：熔断打开之后会不会继续被敲

| 断言 | 结果 |
|---|---|
| C1 失败把 A 的熔断器打开 | HTTP=200 state=**OPEN** |
| C2 OPEN 的候选**被跳过** | 桩A **3→3**（增量为 0）桩B 1→2 |
| C3 全候选不可用 → 快速失败 | HTTP=**503** type=**circuit_open** 耗时 **32ms**，两桩计数均不变 |

C2 的"增量 0"是"跳过而不是试一次被拒再换家"唯一的证明方式。

C 段还观察到一个值得记下来的现象：**熔断器会在一次请求中途翻到 OPEN**。
第 3 个请求里桩B 的重试进行到一半就够阈值了，第 3 次尝试被当场拒绝，
于是那一次请求的失败类型是 `circuit_open` 而不是 `upstream_error`。
这是对的（网关真的没发那次请求），但它意味着"同一个请求可能前半段是上游错误、
后半段是熔断"，排查时别把两者当成互斥的。

单元测试：**124 → 141**（+17）。

## 10. 已知边界

1. **流式空正文不做转移。** 流式的空正文只有到流结束才能判定，而那时收尾帧已经下发；
   再换一家重放会让客户端在"一个 finish_reason"之后又看到新正文。保持 F0 的 `200 + length` 透传。
   （非流式的空正文**会**触发转移。）
2. **一次请求只预扣一次，但故障期可能真的花掉 N 次的钱** → 配额上限会被小幅突破。
   方向与 F1 一致：少扣可追、多扣不可逆。
3. **中间尝试不入账本**（沿用 F1 边界 11）。F1 里这还是理论风险，F2 把它变成必然路径——
   一次请求最多 4 次上游调用、账本只记最终那一次成功的。要真修需要"每次尝试单独落账"。
4. **4xx 会计入熔断窗口。** resilience4j 默认把所有异常都算失败，
   而 400 是客户端问题、不该让下游的熔断器背。应当配 `ignoreException(...)`，尚未做。
   （真机 B3 用的就是这个特性：用 400 把 A 的熔断器打开，而不牵连 B。）
5. **候选顺序是静态的**：没有按健康度动态排序、没有权重、没有轮询。
   链首恢复要靠熔断器的 HALF_OPEN 探针（自动半开已开）逐步把流量拿回来。
6. **候选目标不做预检**：不会先探一下备选再决定，直接尝试。
7. **链首不可达时每个请求仍要先烧 3 次重试**，直到熔断打开（需要攒够 `minimum-number-of-calls` 次调用）。
   A2 实测约 5 秒。调小 `minimum-number-of-calls` 能更快打开，但会更容易误判。
8. **熔断状态不持久化**：进程重启后全部回到 CLOSED，故障期重启会有一段"重新学一遍"的窗口。
9. **流中途卡住仍无防护**（F1 边界 5）：`Flux.timeout` 的作用域只有首元素，
   首片之后一直不吐字不会触发任何超时，因此也不会触发转移。
